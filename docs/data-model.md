# 言の葉を置く — Data Model v0.1

## 1. 設計方針

KOTONOHAでは、ユーザーではなく「言の葉」を中心にデータを構成する。

基本的な関係は、

`場所 → 言の葉 → 繋がった言葉`

とする。

## 2. Kotonoha

新しく場所に置かれた1件の言の葉を表す。

想定項目:

| 項目 | 内容 |
|---|---|
| id | シーケンシャルな言の葉ID。主キー。 |
| parent_id | 言葉を繋いだ場合の親言の葉ID。新規に置く場合はNULL。 |
| installation_id | 内部的な匿名端末識別子。利用者には公開しない。 |
| latitude | 撮影時の緯度 |
| longitude | 撮影時の経度 |
| captured_at | 写真撮影日時 |
| created_at | サーバー登録日時 |
| photo_path | 縮小・圧縮済み写真の保存先 |
| comment | 50文字以内の言葉 |
| status | 公開状態。ACTIVE / HIDDEN / DELETED等を想定。 |

## 3. 新規の言の葉

利用者が「言の葉を置く」で新規作成した場合:

- `parent_id = NULL`
- 写真あり
- 50文字以内の言葉あり
- 撮影位置あり
- 撮影日時あり

## 4. 言葉を繋ぐ

既存の言の葉に言葉を繋ぐ場合、新しい写真は持たない。

想定項目:

| 項目 | 内容 |
|---|---|
| id | シーケンシャルな言の葉ID |
| parent_id | 繋ぎ先となる親言の葉ID |
| installation_id | 内部的な匿名端末識別子 |
| created_at | 登録日時 |
| comment | 50文字以内の言葉 |
| status | 公開状態 |

位置情報については、言葉を繋いだ時点の現在地を監査・不正対策目的で保持するかを実装設計時に確定する。利用者に公開する情報ではない。

## 5. スレッド構造

言葉を繋ぐたびに親IDを記録する。

例:

```text
言の葉 #100
├─ 言葉 #101
│  └─ 言葉 #103
└─ 言葉 #102
```

この構造により、元の言の葉を起点として言葉の連鎖を取得できる。

## 6. 匿名識別

MACアドレスは使用しない。

端末・アプリの初回利用時等にランダムな `installation_id` を生成し、サーバー側で以下に利用する。

- 5分間の新規投稿制限
- 不正利用対策
- 通報対応
- 将来的な利用制限

`installation_id` は公開APIのレスポンスに含めない。

## 7. Report

通報情報を別テーブルで管理する。

想定項目:

| 項目 | 内容 |
|---|---|
| id | 通報ID |
| kotonoha_id | 通報対象の言の葉ID |
| installation_id | 通報元の匿名識別子。必要性を見て保持。 |
| reason | 通報理由 |
| created_at | 通報日時 |
| status | 対応状態 |

## 8. 管理者による削除

言の葉は原則として論理削除とする。

`status` を変更することで利用者から非表示にし、管理上必要な履歴を保持できる構成とする。

## 9. 場所の扱い

v0.1では、言の葉ごとに緯度・経度を保持する。

同一地点・近接地点の言の葉をグループとして扱う表示ロジックはアプリ/API側で実装する。

将来的に投稿数が増えた場合、地理空間検索や場所を表す独立エンティティの導入を検討する。
