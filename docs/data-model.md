# 言の葉を置く — Data Model v0.1

## 1. 設計方針

KOTONOHAでは、ユーザーではなく「言の葉」を中心にデータを構成する。

基本的な関係は、

`場所 → 言の葉 → 繋がった言葉`

とする。

v0.1の基本DBは以下の3テーブルとする。

- `kotonoha` — 言の葉本体と、そこに繋がる言葉
- `reports` — 通報履歴
- `block_list` — 利用停止対象の匿名installation ID

## 2. Kotonoha

新しく場所に置かれた1件の言の葉、および既存の言の葉に繋がる言葉を表す。

想定項目:

| 項目 | 内容 |
|---|---|
| id | シーケンシャルなID。主キー。 |
| parent_id | 言葉を繋いだ場合の親ID。新規に置く場合はNULL。 |
| installation_id | 内部的な匿名端末識別子。利用者には公開しない。 |
| latitude | 新規に置く場合の撮影時の緯度。言葉を繋ぐ場合は現在地を必要に応じて保持。 |
| longitude | 新規に置く場合の撮影時の経度。言葉を繋ぐ場合は現在地を必要に応じて保持。 |
| captured_at | 新規に置く写真の撮影日時。言葉を繋ぐ場合はNULL。 |
| created_at | サーバー登録日時 |
| photo_path | 新規に置く言の葉の縮小・圧縮済み写真の保存先。言葉を繋ぐ場合はNULL。 |
| comment | 50文字以内の言葉 |
| status | 公開状態。ACTIVE / HIDDEN / DELETED等を想定。 |

## 3. 新規の言の葉

利用者が「言の葉を置く」で新規作成した場合:

- `parent_id = NULL`
- 写真あり
- 50文字以内の言葉あり
- 撮影位置あり
- 撮影日時あり

## 4. 言葉を繋ぐ

既存の言の葉に言葉を繋ぐ場合、新しい写真は持たない。

- 50文字以内の言葉だけを登録する。
- 対象となる言の葉IDを `parent_id` として記録する。
- 元の言の葉の写真は変更しない。
- 誰が繋いだかは利用者には表示しない。

想定項目は `kotonoha` テーブルで共通管理する。

## 5. スレッド構造

言葉を繋ぐたびに親IDを記録する。

例:

```text
言の葉 #100
├─ 言葉 #101
│  └─ 言葉 #103
└─ 言葉 #102
```

この構造により、元の言の葉を起点として言葉の連鎖を取得できる。

## 6. 匿名識別

MACアドレスは使用しない。

端末・アプリの初回利用時等にランダムな `installation_id` を生成し、サーバー側で以下に利用する。

- 5分間の新規投稿制限
- 不正利用対策
- 通報対応
- 将来的な利用制限

`installation_id` は公開APIのレスポンスに含めない。

## 7. Reports

通報は別テーブルで履歴を保持する。

通報された内容を管理者が確認した記録を残せるようにする。

想定項目:

| 項目 | 内容 |
|---|---|
| id | 通報ID |
| kotonoha_id | 通報対象のID |
| reporter_installation_id | 通報元の匿名識別子 |
| reason | 通報理由 |
| created_at | 通報日時 |
| status | 未確認 / 確認済み / 対応済み等の状態 |
| admin_note | 管理者による確認・対応メモ |
| reviewed_at | 管理者が確認した日時 |

通報そのものは削除せず、管理者の確認履歴として残す。

## 8. Block List

不正利用や悪質な投稿が確認されたinstallation IDを利用停止対象として管理する。

想定項目:

| 項目 | 内容 |
|---|---|
| id | 管理ID |
| installation_id | ブロック対象の匿名識別子 |
| reason | ブロック理由 |
| created_at | ブロック日時 |
| status | 有効 / 無効 |
| admin_note | 管理者メモ |

## 9. 管理者による削除

言の葉は原則として論理削除とする。

`status` を変更することで利用者から非表示にし、管理上必要な履歴を保持できる構成とする。

通報履歴は残したまま、対象の言の葉を非表示・削除扱いにできる。

## 10. 場所の扱い

v0.1では、言の葉ごとに緯度・経度を保持する。

同一地点・近接地点の言の葉をグループとして扱う表示ロジックはアプリ/API側で実装する。

将来的に投稿数が増えた場合、地理空間検索や場所を表す独立エンティティの導入を検討する。
